# 考勤异常日历接口

基础路径：`/api/attendance/calendar`

统一返回结构：`ReturnInfo<T>`

公共规则：
- Content-Type：`application/x-www-form-urlencoded`
- tokenID 通过 query 参数或请求头传入
- 查询接口已标注 `@ScopeAuthRequired`
- `talentCode` 不传时，默认查询当前登录人的考勤日历
- 查询他人数据时，当前用户必须对该员工所属组织有权限
- 快照缺失时接口不报错，`hasSnapshot=false`，`snapshot=null`，仍返回可查询到的排班和业务明细

## 1. 考勤异常日历月视图查询

`POST /api/attendance/calendar/month`

查询指定员工某个月的考勤日历状态和月度统计。

该接口只读，不写库。当前实现读取 `whd_attendance.attendance_calendar_day_snapshot` 日快照表，不在查询时重新计算考勤结果。

### 查询条件

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| talentCode | String | 否 | 员工编码；为空时查询当前登录人 |
| yearMonth | String | 否 | 查询年月，格式 `yyyy-MM`；为空时查询当前月 |

### 返回字段

| 字段 | 说明 |
|------|------|
| talentCode | 员工编码 |
| talentName | 员工姓名 |
| deptCode | 组织编码 |
| deptName | 组织名称 |
| yearMonth | 查询年月，格式 `yyyy-MM` |
| startDate | 月开始日期，格式 `yyyy-MM-dd` |
| endDate | 月结束日期，格式 `yyyy-MM-dd` |
| stats | 月度统计信息 |
| days | 每日状态列表 |

## 3. 考勤异常日历快照手动刷新

`POST /api/attendance/calendar/snapshot/refresh`

后台手动刷新指定员工指定日期范围的考勤异常日历快照。只给后台测试、运维、问题修复使用，前端普通业务页面不接这个接口。

### 请求参数

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| talentCode | String | 是 | 员工编码 |
| startDate | String | 是 | 开始日期，格式 `yyyy-MM-dd` |
| endDate | String | 是 | 结束日期，格式 `yyyy-MM-dd` |
| refreshMode | String | 否 | 刷新模式，为空时默认 `manual_refresh` |

### 请求示例

```
Content-Type: application/x-www-form-urlencoded

talentCode=10030&startDate=2026-05-01&endDate=2026-05-31&refreshMode=manual_refresh
```

### 返回示例

```json
{
  "success": true,
  "data": {
    "totalCount": 31,
    "successCount": 31,
    "failCount": 0,
    "failedItems": []
  },
  "total": null,
  "currPage": null,
  "message": "ok",
  "messageType": 0
}
```

### 返回字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| totalCount | int | 总处理天数 |
| successCount | int | 成功天数 |
| failCount | int | 失败天数 |
| failedItems | List | 失败明细，每条包含日期和失败原因 |

### 参数校验

1. `talentCode` 必填
2. `startDate` 必填，格式 yyyy-MM-dd
3. `endDate` 必填，格式 yyyy-MM-dd
4. `endDate` 不能小于 `startDate`
5. 日期范围最大 31 天

### 权限规则

1. 接口标注 `@ScopeAuthRequired`
2. 系统管理员可刷新全部员工
3. 当前登录人可刷新本人
4. HR、考勤员、部门负责人只能刷新权限部门范围内员工
5. 判断方式：先根据 `talentCode` 查询员工所属 `deptCode`，再判断是否在 `UserAuthContext.getDeptScopes()` 内

### 业务规则

1. 该接口不新增表，不直接写 SQL
2. 该接口只调用现有快照刷新服务 `AttendanceCalendarDaySnapshotRefreshService.refreshRange`
3. 日期范围限制 31 天，避免一次手动刷新大量数据拖垮服务

## 快照刷新事件接入规则

`AttendanceCalendarSnapshotEventService` 当前作为通用事件登记服务使用。它只负责登记哪些员工、哪些日期需要刷新 `attendance_calendar_day_snapshot`，不直接重新计算快照。

当前已接入事件来源：打卡导入、排班编辑、排班时间修订、调班、档案保存。

补签、请假、出差、加班审批生效链路尚未设计，当前不在这些业务中强行补事件接入。后续实现对应业务接口时，必须在“审批通过并正式生效”的位置调用 `AttendanceCalendarSnapshotEventService.markDirty...`。

### 后续业务接入点

| 业务 | 接入时机 | 刷新范围 | 调用方式 |
|------|----------|----------|----------|
| 补签 | 补签审批通过并生成或修正有效打卡记录后 | 补签员工、补签日期 | `markDirtyOneDay` |
| 请假 | 请假审批通过，请假明细正式生效后 | 请假员工、请假开始日期到结束日期 | `markDirty` |
| 出差 | 出差审批通过，出差记录正式生效后 | 出差员工、出差开始日期到结束日期 | `markDirty` |
| 加班 | 加班审批通过，加班明细正式生效后 | 加班员工、加班日期 | `markDirtyOneDay` |

### 事件类型固定值

| 业务 | eventType | bizType | bizId |
|------|-----------|---------|-------|
| 补签 | `supplement` | `attendance_supplement` | 补签申请主键ID，缺少主键时传补签单号 |
| 请假 | `leave` | `leave_request` | 请假申请主键ID，缺少主键时传请假单号 |
| 出差 | `business_trip` | `business_trip` | 出差申请主键ID，缺少主键时传出差单号 |
| 加班 | `overtime` | `overtime_request` | 加班申请主键ID，缺少主键时传加班单号 |

### 调用规则

1. 单日影响调用 `markDirtyOneDay(talentCode, attendanceDate, eventType, bizType, bizId)`。
2. 跨天影响调用 `markDirty(talentCode, startDate, endDate, eventType, bizType, bizId)`。
3. `talentCode` 必须是员工编码。
4. `startDate`、`endDate` 必须是业务实际影响的出勤日期范围。
5. 同一业务单据重复触发时，事件服务按员工、日期范围、事件类型、业务类型、业务ID 去重。
